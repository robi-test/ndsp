Accessibility

Our approach to accessibility testing

Automated tools such as WAVE, browser accessibility checkers, and DevTools can quickly identify common issues such as missing alternative text, insufficient colour contrast, and certain structural problems. However, automated testing alone can only detect a proportion of accessibility issues and cannot determine whether a user can successfully complete tasks.

The majority of WCAG compliance still relies on manual testing, semantic review, screen-reader testing, and understanding whether real users can successfully complete their tasks.

  • 20% automated tools (WAVE, Axe, Lighthouse)
  • 40% manual WCAG walkthrough
  • 20% screen-reader testing
  • 20% user research and real-user validation

To achieve a comprehensive assessment, we combine automated checks with manual testing. This includes:

  • Reviewing semantic HTML, ARIA roles, landmarks, and programmatically determined relationships.
  • Exploring the Accessibility Tree using browser developer tools.
  • Testing keyboard-only navigation and focus management.
  • Conducting criterion-by-criterion walkthroughs against WCAG 2.2 success criteria.
  • Using screen readers such as NVDA, Narrator, and VoiceOver to understand the actual user experience.
  • Reviewing code where necessary to verify accessibility implementation.

Finally, no accessibility audit is complete without involving real users. User research with people who have a range of access needs provides insights that automated tools and heuristic reviews cannot uncover, helping teams understand how accessibility issues affect real-world task completion, comprehension, and user confidence.

Minimum audit standard for NDSP

A page should only be considered "tested" when it has been:

  • Reviewed against every WCAG 2.2 criterion
  • Tested with keyboard only
  • Run through WAVE/Axe
  • Checked in the accessibility tree
  • Spot-checked with a screen reader
  • Logged in the audit register with evidence and recommendations
